# /lw-check：检查代码改动

核对改动是否破坏行为或已有约束，指出要修的问题、证据和验证缺口。想看改了什么或生成合入报告时用 `lw-review`。

## 1. 选择检查范围

`LW = python3 ~/.light-work/lw.py`。手动参数来自 `$ARGUMENTS`，宿主未展开时取命令名后的内容。

| 调用方式 | 取材料 |
|---|---|
| 手动，无参数 | `$LW check`，最近一条台账改动 |
| 手动，指定条目 | `$LW check C-xxx`，该条已收尾的各轮改动 |
| 手动，`all` / `a` | `$LW check all`，全部台账条目已收尾的改动 |
| 手动，`branch` / `b` | `$LW check branch`，全分支，包括最初开发和后续改动 |
| 编辑流程调用 | `$LW check --base <本轮编辑前的 tree SHA> --current-entry C-xxx`，本轮正在做的改动 |

只在需要专项核对时调用 check。输出标题标明范围。单条和内部调用只检查选定 diff 及涉及的约束。缺少条目收尾点或本轮起点时说明缺少证据。`all` 可用 `$LW conflicts --recorded-only` 补充台账条目间的重叠和回退，`branch` 可用 `$LW conflicts`。需要运行测试时选与本次范围最相关的检查，并说明实际结果。

## 2. 逐项判定

按风险从高到低：

1. **回退/改写**（conflicts 输出）：后面的条目删掉了前面条目加的代码。读两条条目的意图和约束，判断是"有意替换"（应该有 supersedes）还是"改坏了"。以当前代码及约束是否仍成立作为判断依据。
2. **热点**：同一个函数被多个条目改过。读当前代码，确认每个相关条目的约束**同时**成立。多条约束在同一处互相矛盾的，就是需求冲突，必须让用户拍板。
3. **本次范围内的有效约束**：逐条判定 ✓ / ✗ / ?，✗ 和 ? 给出 `文件:行` 证据，并指出是哪个条目哪一轮引入的。
4. **影响面**：删除或改了签名的符号，检查剩下的调用方。
5. **全分支中的未登记改动**：不属于任何条目的文件，看改了什么，判断是不是顺手改或被带出来的。
6. **反复修改 ≥3 轮的条目**：重点看最终版本是否把早期轮次的修复又改回去了。
7. **open、未验证、假设**：原样列出，不替用户假装已验证。

不审代码风格，只看行为。

## 3. 输出（一屏内）

```
/lw-check · feature/voice-search · 全部台账改动 · 7 条目 · 12 文件
✗ 改坏   C-006 R2 删掉了 C-003 加的空值判断 — voice.ts:41（C-003.1 不再成立）
✗ 冲突   C-004.1「空结果不进 error」与 C-007.2「所有失败统一进 error」— handleResult 同一分支
✗ 测试   voice.test.ts › empty result 失败
?  存疑   C-002.2 网络错误仍走 error：catch 里多了 return，需要真机确认
⚠ 热点   handleResult 被 C-003 → C-004 → C-006 → C-007 改过 4 次
⚠ 未验证 C-004 真机未跑；C-006 没有测试
⚠ 待拍板 C-006 假设超时 8s 和后端一致
✓ 通过   11 条约束
```

排序 ✗ → ? → ⚠ → ✓。全部通过就一行：`✓ N 条约束全部通过，未验证 M 项：…`

## 4. 之后

列出需要处理的发现。用户要求修复时进入修改流程。
- 用户同意修：按 lw-record → lw-edit → lw-review 正常流程处理（修复本身也是一条台账）
- 用户对冲突拍板：输的那条用新条目 `supersedes`，不改旧条目
- 未登记改动确认是有意的：补进对应条目的 `文件`，或开一条 `chore`
