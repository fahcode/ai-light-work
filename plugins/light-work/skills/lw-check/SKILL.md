# /lw-check：台账改动的冲突与回归检查

检查清单全部来自台账，用户不用描述"查什么"。参数：`$ARGUMENTS`（Claude Code 会替换成命令后面的文字；Codex 等工具里不替换，就取用户消息里命令名后面的内容，没有就是空）
- 空：台账范围（台账起点到当前工作区的所有改动）
- `C-xxx`：只看这一条的所有轮次，加上与它重叠的其他条目
- `增量`：只看上次收尾点之后
- `全分支`：包括一开始的功能开发

`LW = python3 ~/.light-work/lw.py`

## 1. 取材料（确定性）

```bash
$LW conflicts                 # 条目之间：回退/改写、热点、反复修改、需求更替链
$LW check                     # 台账范围：约束、影响面、未登记改动、未验证、假设、open
#   参数为 C-xxx  → $LW check --entry C-xxx
#   参数为 增量    → $LW check --since-checkpoint
#   参数为 全分支  → $LW check --branch
```

项目里能找到现成的测试命令（package.json 的 scripts、Makefile、CI 配置）就先跑一遍相关测试，失败的用例放在最前面。

## 2. 逐项判定

按风险从高到低：

1. **回退/改写**（conflicts 输出）：后面的条目删掉了前面条目加的代码。读两条条目的意图和约束，判断是"有意替换"（应该有 supersedes）还是"改坏了"。没有 supersedes 却改掉了，默认按改坏处理。
2. **热点**：同一个函数被多个条目改过。读当前代码，确认每个相关条目的约束**同时**成立。多条约束在同一处互相矛盾的，就是需求冲突，必须让用户拍板。
3. **全部有效约束**：逐条判定 ✓ / ✗ / ?，✗ 和 ? 给出 `文件:行` 证据，并指出是哪个条目哪一轮引入的。
4. **影响面**：删除或改了签名的符号，检查剩下的调用方。
5. **未登记改动**：不属于任何条目的文件，看改了什么，判断是不是顺手改或被带出来的。
6. **反复修改 ≥3 轮的条目**：重点看最终版本是否把早期轮次的修复又改回去了。
7. **open、未验证、假设**：原样列出，不替用户假装已验证。

不审代码风格，只看行为。

## 3. 输出（一屏内）

```
/lw-check · feature/voice-search · 台账范围 · 7 条目 · 12 文件
✗ 改坏   C-006 R2 删掉了 C-003 加的空值判断 — voice.ts:41（C-003.1 不再成立）
✗ 冲突   C-004.1「空结果不进 error」与 C-007.2「所有失败统一进 error」— handleResult 同一分支
✗ 测试   voice.test.ts › empty result 失败
?  存疑   C-002.2 网络错误仍走 error：catch 里多了 return，需要真机确认
⚠ 热点   handleResult 被 C-003 → C-004 → C-006 → C-007 改过 4 次
⚠ 未登记 utils/format.ts 改了日期格式，不属于任何条目
⚠ 未验证 C-004 真机未跑；C-006 没有测试
⚠ 待拍板 C-006 假设超时 8s 和后端一致
✓ 通过   11 条约束
```

排序 ✗ → ? → ⚠ → ✓。全部通过就一行：`✓ N 条约束全部通过，未验证 M 项：…`

## 4. 之后

最后只问一句："要我修 ✗ 项吗？需求冲突的那条你定一下用哪个。"
- 用户同意修：按 lw-record → lw-edit → lw-review 正常流程处理（修复本身也是一条台账）
- 用户对冲突拍板：输的那条用新条目 `supersedes`，不改旧条目
- 未登记改动确认是有意的：补进对应条目的 `文件`，或开一条 `chore`
