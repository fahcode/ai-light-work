# /lw-report：台账改动报告

范围是**台账记录的改动**，不是整个分支。整个分支用 `/lw-branch`。参数：`$ARGUMENTS`（Claude Code 会替换成命令后面的文字；Codex 等工具里不替换，就取用户消息里命令名后面的内容，没有就是空）

`LW = python3 ~/.light-work/lw.py`

## A. 不带参数：所有台账改动

### 1. 取材料

```bash
$LW check --ledger --hunks 8   # 台账范围的级别、约束、影响面、未登记改动、关键片段
$LW conflicts                  # 热点和回退，用于"风险"
$LW stats
```

再读台账全文（`.light-work/<分支>.md`）。不用单独输出，但先按 /lw-check 的逻辑把约束判一遍，结果写进报告。

### 2. 写报告（Markdown，按这个结构）

````markdown
# feature/voice-search · 台账改动报告
> 一句话：功能完成后 7 次改动（3 bug / 4 需求变更），集中在 handleResult 和 EmptyTip
> 约束核对：14 条，✓ 12 ｜ ✗ 0 ｜ ? 2
> 需要你：拍板 2 项、看 3 处代码，约 5 分钟

## 改动时间线
| ID | 日期 | 类型 | 用户原话 | 改了什么 | 级别 | 状态 | 验证 |
|---|---|---|---|---|---|---|---|

## 改动点流程图
（mermaid flowchart：画原始功能主流程，每个被台账改过的节点 :::changed，节点文字带条目 ID，
 例如 `B{res 为空? C-003,C-005}:::changed`；被删除的路径用虚线并标"已删除 C-006"）

## 阅读顺序（≤7 步）
1. `文件:行` — 先看这里的原因（关联条目）

## 风险
- 热点 / 回退 / 反复修改 / 未登记改动，每条都要有依据（条目 ID、文件:行）

## 待拍板
- 所有未确认的假设和约束冲突

## 给测试的回归清单
| # | 操作步骤 | 期望结果 | 来源 | 新/旧 |
|---|---|---|---|---|
| 1 | 不说话直接松手 | 提示"换个说法试试"，不出现错误页 | C-005.1 | 新 |
| 2 | 断网后说话 | 出现错误页和重试按钮 | C-002.2 | 回归 |

（台账里所有有效约束都要翻译成测试能执行的步骤；台账改动新引入或改变的行为标"新"，被改动波及、需要回归的旧行为标"回归"）

## 未验证汇总
````

### 3. 生成页面

把上面的报告 Markdown 直接通过标准输入交给脚本，不要另存文件：

```bash
$LW view --title "台账改动报告" --open <<'LW_REPORT'
（上面写好的报告全文）
LW_REPORT
```

页面是 `.light-work/<分支>.html`（每次生成都覆盖），末尾自动附上台账原文。在聊天里只回三行结论和页面路径。

## B. 带参数 C-xxx：单条详报

```bash
$LW score --entry C-xxx --hunks 8   # 这一条所有轮次的改动
$LW conflicts                        # 看它和别的条目的重叠
```

写一份单条详报，不受卡片级别限制，按 L3 规格展开——用户原话与每轮修改过程、修改前后流程对比图（两个 mermaid 或一个图里标出改动）、关键片段（真实 diff）、影响面、与其他条目的重叠、约束核对、这一条的测试清单。然后同样通过标准输入生成页面：`$LW view --title "C-xxx 详报" --open <<'LW_REPORT' … LW_REPORT`。

## 规则

- 片段只取真实 diff，图只画真实存在的函数和分支
- 最上面三行是结论
- 报告是给人看的，不要粘贴整段台账
