# lw-review：自检，然后给用户看 review 卡片

目标：用户 30 秒内看懂这次改了什么、能不能放心。

`LW = python3 ~/.light-work/lw.py`

## 1. 拿事实，不凭记忆

```bash
$LW score    # 本轮改动（上次收尾点 → 现在）：级别和依据、影响面、要核对的约束、关键片段
```

级别以脚本为准。有明确理由时可以上调一级，在卡片里说明；不能下调。

## 2. 自检

score 列出的每条约束，都打开当前代码判断：
- ✓ 仍成立：给出 `文件:行`
- ✗ 被这次改坏了：是你带坏的就**当场修好**，然后回到第 1 步；是用户新要求和旧约束冲突，放进"待你拍板"
- ? 从代码判断不了：放进"待你拍板"

score 里的 ⚠ 也要回应：
- 删了还有人引用的符号：修好
- 改了不属于本条的文件：要么是本次需要的（补进条目），要么在卡片里说明是顺手改的
- 改了逻辑却没动测试：在验证里标 ✗

score 列出「一层调用方」时（这些文件没改，但调用了你改过内部逻辑的函数）：打开调用处看一眼。会受影响就写进卡片的影响面，或者当场修好；同名误报直接忽略。不用为它升级别。

## 3. 补全条目

更新 lw-record 写的那一条：
- `文件`：按实际改动修正
- `约束`：按最终实现修正
- `验证`：`✓ 实际跑的命令 → 结果 ｜ ✗ 没做的`，例如 `✓ pnpm test voice → 16 passed`。没跑就写 ✗，不能写"应该没问题"
- `根因`（bug）：一句话加 `文件:行`
- `过程`：本轮做了什么，如 `R2 网络错误改回 error 态`
- `级别`：score 的结果（多轮取最大值）

状态不用管：`git commit` 时插件会自动把它标成已定稿。用户明确说"可以""就这样"时，也可以直接改成 `settled`。然后运行 `$LW lint`，有问题就改到通过。

## 4. 输出卡片

按级别套用 `references/cards.md` 的模板：
- 最上面三行是结论：**改了什么、约束还成不成立、需要用户做什么**
- 代码片段只取自 score 给的真实 diff，标注 `文件:行`
- 图只画 diff 里真实存在的函数和分支，改动的节点标 `:::changed`；画不出就不画
- lw-edit 里的"顺带发现"放在最后一行

L0、L1 只在聊天里输出。**L2、L3 有流程图**，聊天里不一定能渲染，所以同时生成一页网页，并在卡片末尾附上路径：

```bash
$LW view --title "C-005 review" <<'LW_REPORT'
（卡片全文）
LW_REPORT
```

## 5. 记录收尾点

```bash
$LW checkpoint --entry C-005
```

一定要带 `--entry`：/lw-check 要靠它知道每一轮改动属于哪一条。
